## 4. Findings

### API-001 (SW-013) — No HTTP-level route test proves the auth, RBAC and 404 contract for any route
- Severity: P1 · Confidence: CONFIRMED · Module: all
- **Description.** CLAUDE.md §15 requires two kinds of test for every sub-phase:
  - a test that another user gets 404;
  - RBAC tests for every role, covering both allowed and refused.
  The only backend test that builds the Express app is `src/app.cors.test.ts`. `middleware/rbac.test.ts` unit-tests the middleware with fake requests. `finance.routes.test.ts` and `reports.routes.test.ts` test exported query parsers. None of them sends requests through the real route stack.
- **Consequence.** Nothing catches a regression such as a missing `rbac()` on a new route, a wrong permission key, or a router mounted ahead of another. The e2e suites (`e2e/*.spec.ts`) cover only a few flows.
- Evidence: `grep -rl "supertest\|request(app\|createApp" backend/src --include=*.test.ts` → `src/app.cors.test.ts` only.
- Affected users: all. Business impact: permission regressions ship silently.
- **Recommended fix.** Add a supertest suite that walks every route in the inventory. For each route:
  - send an unauthenticated request and expect 401;
  - send a request with a role that lacks the permission and expect 403;
  - send a request for another tenant's row and expect 404;
  - generate the cases from the route table so a new route fails CI until it is classified.
- Dependencies: test DB (somwave_qa). Complexity: M. Verification: CI run; mutate one `rbac()` and watch the suite fail.

### API-002 (SW-003) — HR endpoints trust `employeeId` from the request body: any STAFF member can check in or out, or file leave, for any employee, and can read every employee's leave and attendance
- Severity: P1 · Confidence: CONFIRMED (code path) · Module: HR (attendance, leave)
- **Description.** These routes take the employee from the request body:
  - `POST /api/v1/attendance/check-in` and `/check-out` take `employeeId` from the body (`checkInSchema`, `packages/shared/src/schemas/attendance.ts`).
  - `POST /api/v1/leave-requests` likewise takes `employeeId` from the body (`createLeaveRequestSchema`).
  The controllers pass it straight through, with no check against `req.authUser`:
  - `controllers/ops-extra.controller.ts:114-130`: `hr.checkIn(employeeId)`
  - `controllers/ops-extra.controller.ts:140-142`: `hr.createLeaveRequest(req.body)`, with no actor passed
  The services only check that the employee exists (`services/hr.service.ts:129-131`, `:208-214`).
  The read side is unscoped too:
  - `GET /leave-requests` returns every employee's leave, including the free-text `reason` (`hr.service.ts:186-200`).
  - `GET /attendance` returns everyone's attendance (`hr.service.ts:110`).
  - `PATCH /leave-requests/:id` has no guard against approving one's own request (`hr.service.ts:246-256`).
  The seed grants `attendance.create`, `leave.read` and `leave.create` to **STAFF** (`backend/prisma/seed.ts:180-184`). Any STAFF user can therefore record attendance for colleagues, or file leave on their behalf, and read colleagues' sick-leave reasons. The UI makes this easier, because both forms have a free employee picker (`frontend/src/features/ops/LeavePage.tsx:161`, `AttendancePage.tsx:18`).
- **Reproduction** (needs a STAFF login; not run in production):
  1. Sign in as STAFF A.
  2. `POST /api/v1/attendance/check-in {"employeeId":"<B's employee id>"}` returns 201.
  3. `POST /api/v1/leave-requests {"employeeId":"<B>","type":"SICK",…}` returns 201.
- Expected: STAFF can act only on their own `Employee` (derived from `req.authUser.id`), and only HR/MANAGER sees everyone's rows. Actual: unrestricted.
- Root cause: ownership is taken from client input instead of the session (§11 "per-user scoping has no exceptions").
- Affected users: all employees. Business impact: falsified attendance and leave records, which feed payroll; disclosure of medical leave reasons.
- **Recommended fix.**
  - Derive `employeeId` from the session for check-in/out and for leave creation, unless the actor holds a dedicated `attendance.manage`/`leave.manage` permission.
  - Scope `GET /leave-requests` and `GET /attendance` to the caller's own rows unless they hold `leave.update`/`attendance.manage`.
  - Forbid approving a leave request whose employee is the actor.
- Dependencies: a decision on the HR permission model. Complexity: S–M.
- Verification: API tests as STAFF A against B's employee id expect 403/404; `LEAVE_READ`-only users see only their own rows.

### API-003 (SW-024) — Global search ignores project membership and leaks names of all projects and tasks
- Severity: P2 · Confidence: CONFIRMED (code path) · Module: Search
- **Description.** `GET /api/v1/search` gates projects only on `projects.read` and tasks only on `tasks.read`. It then queries `prisma.project.findMany({ where: { deletedAt: null, name: contains } })` and the equivalent for tasks, with **no `projectScope(actor)`** (`services/search.service.ts:32-40` and `:73-82`). Task hits include the parent project's name.
- **Contrast.** The list endpoints do apply membership scope:
  - `GET /projects`: `project.service.ts:96-101`
  - `GET /tasks`: `task.service.ts` `project: projectScope(actor)`
  - `GET /milestones`: same
- **Consequence.** ENGINEER, QA_ENGINEER and STAFF users (all hold `projects.read`/`tasks.read` per seed) can enumerate the names of every project and task in the company by searching 2-letter strings.
- Expected: search results equal what the user can open. Actual: everything matching.
- Business impact: internal and confidential client project names are disclosed to every engineer, including contractors.
- Fix: apply `project: projectScope(actor)` to the task query, and `...projectScope(actor)` to the project query. Complexity: S.
- Verification: a unit test where a non-member searches a project name and gets 0 hits.

### API-004 (SW-025) — File downloads return 500 for non-Latin-1 filenames; the documents download builds `Content-Disposition` from the raw title
- Severity: P2 · Confidence: CONFIRMED (code path + local Node reproduction) · Module: Documents, Portal, Engineering attachments, Project documentation
- **Description.** Several downloads put the stored name into `Content-Disposition: attachment; filename="${name}"`:
  - `controllers/ops-extra.controller.ts:213`: document title, unsanitised
  - `portal.controller.ts:71`
  - `engineering.controller.ts:349-352`
  - `project-documentation.controller.ts:157`
  The last three strip only `\r\n"\\`. Node's `setHeader` throws `ERR_INVALID_CHAR` for any character above U+00FF. A local reproduction returned `500 ERR_INVALID_CHAR` for `filename="عقد.pdf"`.
- **Consequence.** Arabic is a supported locale (§17), so a document titled or named in Arabic cannot be downloaded. The user gets the generic 500. A `"` in a document title also produces a malformed header.
- Two endpoints are not affected:
  - media sanitises names to `[a-zA-Z0-9._-]` (`media.service.ts:41`);
  - inquiry attachments use `safeFileName` (`project-inquiry-attachment.service.ts:29-39`).
- Fix: build the header with the `content-disposition` package (or RFC 5987: `filename="ascii-fallback"; filename*=UTF-8''<pct-encoded>`) in one shared helper, and use it in all 7 download handlers. Complexity: S.
- Verification: unit test that downloads a file named in Arabic and expects 200 and a correct `filename*`.

### API-005 (SW-026) — Large JSON bodies (up to 35 MB) are parsed before authentication and before the rate limiter
- Severity: P2 · Confidence: CONFIRMED (code) · Module: app.ts
- **Description.** In `app.ts` the body parsers come first:
  - `express.json({limit:'35mb'})` on `/api/v1/media`, `/documents`, `/projects/:id/documentation` and `/engineering/tasks/:id/attachments`;
  - `8mb` on the two inquiry-attachment paths.
  These run at `app.ts:75-82`. `apiRateLimiter` is applied later (`app.ts:89`), and `requireAuth` runs inside the routers.
- **Consequence.** An unauthenticated client can make the server buffer and JSON-parse 35 MB per request, unthrottled until the parse finishes and the limiter runs. A handful of parallel uploads gives CPU and memory amplification. The webhook raw parsers (256 kB) are also mounted before the limiter, but they are small.
- Expected: reject unauthenticated or over-limit callers before reading the body. Actual: the body is read first.
- Business impact: cheap denial of service on a single-VPS deployment.
- **Recommended fix.**
  - Move `apiRateLimiter` ahead of the large parsers.
  - Mount the large parsers inside the routers after `requireAuth`, for example `router.post('/', requireAuth, rbac(...), express.json({limit:'35mb'}), …)`.
  - Better still, switch uploads to presigned S3 PUTs, as §13 already requires.
- Complexity: S (reorder) / L (presigned).
- Verification: an unauthenticated 30 MB POST to `/api/v1/documents` returns 401 before the body is consumed (check memory with `autocannon`).

### API-006 (SW-015) — 2FA login has no per-account attempt limit, and the challenge token is reusable for 5 minutes
- Severity: P2 · Confidence: CONFIRMED (code) · Module: Auth
- **Description.** `POST /auth/login/2fa` runs `loginAccountRateLimiter`, but that limiter skips when the body has no `email` (`middleware/rateLimit.ts:44-51`). `verifyTwoFactorSchema` carries `challengeToken` and `code`, with no email (`packages/shared/src/schemas/auth.ts:14-17`). Only the IP limiter applies: 20 requests per 15 minutes per IP.
- The challenge JWT is valid for 5 minutes and is not consumed when a code is wrong (`services/auth.service.ts:159-188`, `lib/tokens.ts:23-24`). An attacker who already has the password can rotate IPs and retry TOTP and backup codes against one account without any account-level counter.
- The authenticated `/auth/2fa/disable`, `/2fa/confirm` and `/2fa/backup-codes` routes have only the global 100/min limit.
- §13 says "Rate limit login by IP and by account".
- Fix: key a limiter, or a Redis counter, on `challenge.sub`, about 5 failures per challenge and per user per 15 minutes; revoke the challenge after N failures; add the same limiter to the `/2fa/*` routes. Complexity: S.
- Verification: unit test where 6 wrong codes are followed by 429 or a revoked challenge.

### API-007 (SW-027) — Several list endpoints are unbounded or silently truncated, with no `meta`
- Severity: P2 · Confidence: CONFIRMED (code) · Module: Invoices, Tickets, HR, Media, CMS, Leads
- **Unbounded `findMany`, no pagination:**
  - `GET /invoices` (`invoice.service.ts:100-107`)
  - `GET /support-tickets` (`ticket.service.ts:85-91`)
  - `GET /employees` (`hr.service.ts:36-42`)
  - `GET /leave-requests` (`hr.service.ts:186`)
  - `GET /media` (`media.service.ts`, `listMedia`)
  - `GET /cms/subscribers` (`subscriber.service.ts:35-40`)
  - `GET /timesheets` (own rows)
- **Hard `take: 100`, or 50, without `meta.total`, so rows past 100 silently disappear:**
  - `GET /leads` (`inquiry.service.ts`)
  - `GET /job-applications` (`job.service.ts`)
  - `GET /attendance`
  - `GET /audit-logs` (`system.service.ts:5-9`)
  - `GET /notifications` (take 50)
- §10 requires `?page=&pageSize=` with `meta.total`, and §12 requires search, filter and pagination for any table over 10 rows.
- **Side effects on GET:**
  - `GET /invoices` runs `markOverdue()`, an `updateMany`, on every list call (`invoice.service.ts:93-101`). That work belongs in BullMQ (§11).
  - `GET /timesheets` may **create** an `Employee` row (`timesheet.service.ts:35-45`).
- Business impact: an audit log that silently loses entries after 100 rows; slow invoice and ticket pages as data grows.
- Fix: use the `clients`/`documents` pattern (`pageParam` plus a capped service). Move overdue marking to a scheduled job. Complexity: M.
- Verification: seed 150 rows and expect `meta.total` = 150 with page 2 returning 50.

### API-008 (SW-080) — Query validation is hand-rolled per controller; large `page` values become 500s (SUSPECTED)
- Severity: P3 · Confidence: SUSPECTED · Module: users, projects, tasks, milestones
- **Description.** `parsePositiveInt` has no upper bound (`controllers/user.controller.ts:9-12`, with copies in the task, milestone, project and public controllers). `?page=99999999999` gives `skip = (page-1)*take`, which is past Prisma's 32-bit Int limit, so the request is likely to fail validation and return 500 instead of 400.
- Contrast: finance and reports cap `page` (10,000 / 100,000) and reject bad input with 400.
- Fix: one shared `paginationQuerySchema` (Zod) in `packages/shared`, applied with a `validateQuery()` middleware. Complexity: S.
- Verification: `GET /users?page=99999999999` returns 400.

### API-009 (SW-081) — Idempotency-Key missing on several message-sending endpoints; public enforcement checks only that the header exists
- Severity: P3 · Confidence: CONFIRMED · Module: Users, Engineering accounts, Tickets, Engineering invitations
- **Description.** §10 says: "Anything that charges money or sends a message requires an Idempotency-Key header". It is enforced only on `POST /payments`, `POST /payments/evc-plus` and `POST /invoices/:id/send` (`controllers/payment.controller.ts:31,52`, `invoice.controller.ts:61`).
- **Not enforced on:**
  - `POST /users` (sends the invitation email, `user-invitation.service.ts:77`)
  - `POST /users/invitations/:id/resend`
  - `POST /engineering/accounts` and `/:userId/resend` (email, `engineer-account.service.ts:104`)
  - `POST /engineering/projects/:id/invitations` and `/resend`
  - `POST /support-tickets` and `/:id/replies` (messages)
  - `POST /public/project-inquiries/:id/resend`
- `POST /public/inquiries` and `POST /public/careers/:slug/applications` check only that the header is present, not its format (`public.controller.ts:172-175`, `:246-250`). The `KEY_PATTERN` in `lib/idempotency.ts:9` is not reused.
- Payments are safe: the key has a DB unique constraint (`schema.prisma:427`), and replay is checked against the already-scoped invoice (`payments/gateways/evcplus.gateway.ts:39-44`).
- Fix: apply `readIdempotencyKey` plus the replay cache to the endpoints above, or record an explicit exception in an ADR. Complexity: S–M.

### API-010 (SW-076) — Rate limiter uses the in-process memory store
- Severity: P3 · Confidence: CONFIRMED · Module: middleware/rateLimit.ts
- **Description.** None of the six `rateLimit()` instances sets a `store` (`middleware/rateLimit.ts:23-51`), so counters live in each Node process.
- **Consequences:**
  - A container restart or redeploy resets all login and account counters.
  - Running more than one replica multiplies every budget.
  - The `loginAccountRateLimiter` (5 per 15 min per email) can be used to lock a victim out of login by sending bad attempts. That is inherent to account limiting, but worth monitoring.
- Fix: `rate-limit-redis` with the existing ioredis client. Complexity: S.

### API-011 (SW-010) — The central error handler discards the error, and Prisma known errors become 500
- Severity: P3 · Confidence: CONFIRMED · Module: middleware/errorHandler.ts
- **Description.** For non-`AppError` errors the handler logs only `{requestId, errorCategory, httpStatus}` (`errorHandler.ts:27-37`): no message, no stack, no Prisma code. Diagnosing a production 500 is therefore impossible without reproducing it. (This was deliberate, for privacy.)
- Prisma `P2002` (unique violation) and `P2025` (record not found) are not mapped, so races return 500 instead of 409 or 404. Only 5 service files handle `P2002` locally, while 15 `update`/`delete({where:{id}})` call sites exist.
- `JSON.parse` in the EVC webhook is unguarded (`payment.webhook.controller.ts:22`): malformed JSON with a valid signature returns 500. The GitHub webhook does guard it.
- Fix: log `err.name`, the Prisma `code` and a stack trace with redaction; map `P2002`→409 and `P2025`→404 centrally. Complexity: S.

### API-012 (SW-082) — Webhooks bypass access logging and rate limiting
- Severity: P3 · Confidence: CONFIRMED · Module: app.ts
- **Description.** `/api/v1/payments/webhooks` and `/api/v1/github/webhooks` are mounted at `app.ts:65-74`, before `pinoHttp` (`:84`) and before `apiRateLimiter` (`:89`).
- **Consequences:**
  - Payment callbacks, which update invoice status, leave no access-log line.
  - Bursts of bad-signature requests are not limited. Each one is cheap, because the HMAC check runs first.
  - `GITHUB_WEBHOOK_SECRET` is read from `process.env` directly (`github.controller.ts:165`), not from the Zod-validated env (§13).
- Fix: mount `pinoHttp` before the webhook routers, add a dedicated webhook limiter, and add the secret to `lib/env.ts`. Complexity: S.

### API-013 (SW-083) — `validate()` covers only the request body; query and params have no shared schema
- Severity: P3 · Confidence: CONFIRMED · Module: middleware/validate.ts
- **Description.** `validate(schema)` parses only `req.body` (`middleware/validate.ts:9`). Every list filter, `?from`, `?to`, `?search`, `?status`, `?sortBy` and every `:id` is parsed by hand in controllers, three different ways: lenient (`parsePositiveInt`), strict (finance and reports), and ad hoc (`queryString`).
- This conflicts with §11: "validation happens at the boundary, from the shared schema".
- Fix: add `validate({ body, query, params })` and shared query schemas. Complexity: M.

### API-014 (SW-084) — Project documentation routes ignore the `project-documentation.*` permissions
- Severity: P3 · Confidence: CONFIRMED · Module: Project documentation
- **Description.** The 27 routes under `/projects/:projectId/documentation` have no `rbac()` (`routes/project-documentation.routes.ts`). The service checks only project membership and member role (`services/project-documentation.service.ts:25-52`).
- The keys `PROJECT_DOCUMENTATION_READ` and `PROJECT_DOCUMENTATION_MANAGE` exist and are seeded to roles (`packages/shared/src/constants/permissions.ts:73-74`, `seed.ts`), but nothing checks them. Revoking them from a role in `/roles` therefore has no effect, which misleads administrators.
- Fix: add `rbac(PROJECT_DOCUMENTATION_READ)` to reads and `MANAGE` to writes, or remove the keys. Complexity: S.

### API-015 (SW-085) — Finance and Reports skip the controller layer
- Severity: P3 · Confidence: CONFIRMED · Module: finance.routes.ts, reports.routes.ts
- **Description.** Both route files hold inline handlers that parse queries and call services, including CSV building (`finance.routes.ts:308-337`). The §5 layering (route → controller → service) is broken. Prisma is still confined to services.
- Fix: move the handlers to `finance.controller.ts` and `reports.controller.ts`. Complexity: S.

### API-016 (SW-086) — The `?sort=` contract is not implemented; project portfolio sorts and paginates in memory
- Severity: P3 · Confidence: CONFIRMED · Module: Projects
- **Description.** No endpoint parses §10 `?sort=-createdAt,name`.
- `GET /projects/portfolio` accepts `sortBy` and `sortDirection`, loads every matching project, sorts in JavaScript, then slices the page (`services/project.service.ts:413-427`). An unknown `sortBy` is passed through to `a[sortBy]`. That is harmless, but unvalidated.
- Fix: a shared sort parser with a per-endpoint whitelist mapped to Prisma `orderBy`. Complexity: M.

### API-017 (SW-087) — The `X-Request-ID` header and the access-log request id differ
- Severity: P3 · Confidence: CONFIRMED · Module: logging
- **Description.** `pinoHttp({ logger })` is mounted with no `genReqId`, at `app.ts:84`, before `withRequestContext` (`:85`). Two different ids result:
  - pino assigns its own incrementing `req.id`;
  - `withRequestContext` generates a separate UUID for `X-Request-ID` and the error `requestId` (`lib/requestContext.ts:18-20`).
  The finance logger then uses `req.id`, which is pino's id (`finance.routes.ts:29`).
- **Consequence.** A support request quoting `X-Request-ID` cannot be matched to its access-log line.
- Fix: generate the UUID first and pass it as `genReqId`. Complexity: S.

### API-018 (SW-088) — Task review route grants `engineering.read` as an alternative to `engineering.tasks.review`
- Severity: P3 · Confidence: CONFIRMED · Module: Engineering
- **Description.** `rbacAny([ENGINEERING_TASK_REVIEW, ENGINEERING_READ])` sits at `routes/engineering.routes.ts:241-245`, so any engineering reader passes the route gate. The service's `requireReviewer` then limits access to the project manager, REVIEWER or LEAD_ENGINEER member (`services/engineering.service.ts:107-112`), so I found no exploit.
- The route and the docs disagree: `API_REFERENCE.md` documents `V` only.
- Fix: use `rbac(ENGINEERING_TASK_REVIEW)`, or update the docs to match. Complexity: S.

### API-019 (SW-089) — API reference covers less than half the surface
- Severity: P3 · Confidence: CONFIRMED · Module: docs
- **Description.** See §3 "docs/API_REFERENCE.md discrepancies": about 190 endpoints are undocumented, including all of finance, invoices, payments, CMS, public, portal and HR. Four documentation-attachment and visibility routes are missing even in the sections that are covered.
- Fix: generate the reference from the route table, or from OpenAPI via `zod-to-openapi`. Complexity: M.

### API-020 (SW-090) — UI-unreachable endpoints and incomplete CRUD
- Severity: P3 · Confidence: CONFIRMED (static matching) · Module: Clients, Employees, Leads, Portal, Engineering worklog, GitHub, Project documentation
- **Description.** 29 backend routes have no frontend or web caller (listed in §3). The ones that matter for users:
  - `PATCH /clients/:id` and `PATCH /employees/:id`: no edit UI, so CRUD is incomplete (§15).
  - Inquiry attachment list and download, for both admin and client.
  - Time-entry correction and revision history.
  - GitHub task links.
  - Documentation plans: 5 routes.
  - Documentation attachments and delete.
  Separately, there is no update or delete endpoint for draft invoices, clients or leads.
- Fix: decide per route whether to build the UI or remove the route. Complexity: M.
